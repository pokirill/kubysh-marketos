## Запасной выход был заколочен 3 недели, и мы узнали об этом, когда загорелось

В воскресенье у меня перестал грузиться лидерборд. Ни по Wi-Fi, ни с VPN, ни без него. Claude посмотрел логи сервера: с утра до нас не дошел ни один запрос из приложения. Сервер при этом был жив, база тоже, просто к нему никто не приходил.

Я делаю финансовое приложение для iPhone. Код с недавних пор пишет Codex, а Claude ведет диагностику, ставит задачи и проверяет результат. Я в этой схеме продакт, который принимает решения и иногда руками запускает команды на сервере. Про этот инцидент мне хочется рассказать честно, потому что виноват в нем не Яндекс, а мы сами.

## Почему вообще шлюз

В конце августа мы переехали на российский сервер. Потом выяснилось, что у части мобильных операторов по LTE открываются только ресурсы из белых списков. Нашего сервера в них не было. У заметной доли пользователей приложение просто молчало, и мы узнавали об этом по пустым графикам, а не по жалобам.

Решение было такое: поставить перед сервером API Gateway в Yandex Cloud. Он serverless, живет на адресах Яндекса и по LTE открывается. Приложение ходит в шлюз, шлюз пересылает запрос на наш сервер.

Мы не стали класть все яйца в одну корзину. В приложении был запасной маршрут: если шлюз не отвечает, запрос идет на сервер напрямую. Нормальная схема, я был спокоен.

## Что сломалось на самом деле

Шлюз перестал отвечать 11 октября около 7 утра. Это случается с любым облаком, и ради этого запасной маршрут и строился.

Claude воспроизвел проблему отдельным тестом в симуляторе. Оказалось, что запасной маршрут шел не по имени сервера, а по голому IP-адресу. Когда приложение обращается по IP, сервер не понимает, какой из сайтов на нем запрашивают. Он отдает тот, что стоит по умолчанию.

А 17 сентября мы положили на тот же сервер лендинг. С этого дня сайтом по умолчанию стал лендинг. Каждый запрос по запасному маршруту 3 недели получал страницу 404 от лендинга вместо ответа API.

Никто этого не заметил, потому что шлюз работал. Запасной путь не использовался ни разу, и проверить его было нечем.

Починка заняла одну строку в конфиге nginx: пометить API сервером по умолчанию. Я выполнил команду, через минуту загрузился лидерборд, в логах появились запросы.

## Почему одной строки мало

Дальше начался разбор, и он оказался интереснее самой поломки. Claude нашел еще 4 места, где запасной путь был только на бумаге.

**Гонка, которая проигрывала сама себе.** Приложение отправляло запрос в шлюз и через 3 секунды дублировало его напрямую. Если шлюз отказывал мгновенно, он отменял и прямую попытку тоже. То есть быстрый отказ шлюза был хуже медленного.

**Гонка только для двух экранов.** Двойная отправка работала для чата и лидерборда. Синхронизация данных, вход и аналитика ходили только через шлюз и падали вместе с ним.

**Нет паузы после отказа.** Каждый следующий запрос снова шел в упавший шлюз и ждал таймаут. Приложение не запоминало, что шлюз лежит.

**Выключатель за той же дверью.** У нас есть удаленный конфиг, которым можно отключить шлюз для всех. Он загружался через шлюз. Когда шлюз упал, выключить его стало невозможно.

Последний пункт меня зацепил сильнее остальных. Мы сделали аварийный рубильник и повесили его внутри комнаты, которая горит.

## Что сделали

Задачи для Codex Claude написал в тот же день, с критериями приемки, а не с пожеланиями:

1. Запасной маршрут идет сначала по имени сервера, IP только если имя не резолвится.
2. Отказ шлюза не отменяет прямую попытку, прямая стартует сразу после отказа.
3. Двойная отправка для всех запросов: вход, синхронизация, аналитика. Повторы не создают дублей, сервер отсекает их по идентификатору.
4. После отказа шлюз пропускается 10 минут.
5. Конфиг лежит в объектном хранилище Яндекса. Это другой сервис, и при падении serverless он продолжает работать.

Критерий приемки звучал так: шлюз висит, прямой маршрут отвечает, приложение получает ответ быстрее 5 секунд. Для лидерборда, синхронизации и аналитики отдельно. Codex прогнал сетевые тесты, на бэкенде прошли 485 тестов.

## Что потеряли

Приложение устроено так, что бюджет, траты и план живут на телефоне. Человек мог открыть приложение и внести трату, деньги и расчеты не пострадали. Не работали лидерборд, чат и синхронизация.

С аналитикой интереснее. События копятся в очереди на устройстве и уходят, когда связь появляется. Но после починки сервера события все равно не пошли: у части запросов была своя логика повторов, которая снова упиралась в шлюз. Эта часть еще в работе, и я не буду делать вид, что все уже закрыто. Дневные сводки за пропущенные дни мы потеряли.

## Что я из этого вынес

Мне кажется, главный урок не про облака. Запасной путь, по которому ни разу не ходили, не существует. Он существует только на схеме, и схема вас успокаивает ровно до первой аварии.

Второе. Мы сломали API изменением, которое к API не относилось. Лендинг и приложение живут на одном сервере, и правка одного тихо поменяла поведение другого. Ни один тест этого не поймал, потому что тестов на это не было.

Третье, про работу с ИИ. Диагноз занял меньше времени, чем я потратил бы на то, чтобы найти нужного человека в выходной. Но решение повесить конфиг за шлюзом тоже когда-то прошло через ИИ, и никто из нас его не оспорил. Модель проверяет то, что ей показали. Спросить «а что если упадет именно это» все еще моя работа.

Теперь я хочу проверять запасной маршрут регулярно, а не ждать аварии. Пока не решил как: отдельным тестом в каждой сборке или проверкой с внешнего сервера раз в час. Если вы решали похожую задачу, мне правда интересно, какой вариант прижился у вас.
